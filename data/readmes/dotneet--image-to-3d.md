# Image to 3D

1枚の画像から 3Dモデル (GLB) をローカル生成し、ブラウザで確認するアプリ。
生成エンジンは **TRELLIS.2** (Microsoft) の Apple Silicon / MPS ポートを使う。

形状生成のあとに **ポリゴン削減 → UV再展開 → メッシュ修復 → 入力画像の投影 → オートリグ**
をつなげられるステージ式パイプラインになっていて、リグ付き GLB (スキン + アニメーション)
まで一気に出力できる。

```
画像 ─> 前処理 ─> 3D生成 ─> ポリゴン削減 ─> UV展開/リベイク ─> メッシュ修復 ─> 投影 ─> オートリグ ─> GLB
          (TRELLIS.2/MPS) (fast-simplification) (xatlas)      (numpy)              (Blender headless)
```

## 必要なもの

| | |
|---|---|
| ハード | Apple Silicon (M1以降)、unified memory 24GB以上 |
| OS | macOS 12以降 (Metal 拡張を使う場合は 26以降) |
| Python | 3.11以上 (`uv` があると楽) |
| Node.js | 20以上 |
| Blender | 5.x (オートリグに使用。無くても生成はできる) |
| ディスク | 約20GB (依存1GB + モデル重み約15GB) |

## セットアップ

### 1. アプリ本体

```bash
make setup
```

`uv` で `.venv` を作り、バックエンドの依存とフロントエンドの npm パッケージを入れる。

### 2. TRELLIS.2 (生成エンジン)

TRELLIS.2 は torch + Metal 拡張 + Python 3.11 という重い専用環境を要求するので、
**アプリ本体とは別の venv** に隔離して入れる。

先に Metal Toolchain を入れておくと生成が大幅に速くなる (数GBのダウンロード):

```bash
xcodebuild -downloadComponent MetalToolchain
```

続いて:

```bash
make setup-trellis
```

最後に Hugging Face の認証を通す。TRELLIS.2 本体 (MIT) は自由に落とせるが、
内部で使う特徴抽出器と背景除去モデルがゲート付きのため必要:

```bash
vendor/trellis-mac/.venv/bin/hf auth login
```

その上で以下のアクセス申請をする (通常は即時承認):

- <https://huggingface.co/facebook/dinov3-vitl16-pretrain-lvd1689m>
- <https://huggingface.co/briaai/RMBG-2.0>

認証を通してから `make setup-trellis` をもう一度流すと、最後の工程で重み
(合計約15GB) を取得する。中断しても再実行で再開する。`SKIP_WEIGHTS=1` を
付ければ飛ばせるが、その場合は初回生成時にまとめて落ちてくる。

セットアップ状況の確認:

```bash
PYTHONPATH=backend .venv/bin/python -m app.engines.trellis
```

未充足の前提条件は起動後の画面左上「セットアップ」パネルにも出る。

### 3. 起動

```bash
make serve
```

<http://127.0.0.1:8100> を開く。フロントを触りながら開発する場合は `make dev`
(Vite が :5173 で立ち、`/api` を :8100 にプロキシする)。

## 使い方

1. 左パネルに画像をドラッグ&ドロップする (リポジトリ直下の `images/` と `samples/` は初回起動時に自動で取り込まれる)
2. サムネイルを選ぶ
3. 生成プリセットを押す

| プリセット | 内容 |
|---|---|
| 形状のみ生成 | テクスチャベイクを省略。形の確認用 |
| テクスチャ付き生成 (標準) | PBRテクスチャをベイク。生成の標準 |
| 最高品質 (低速) | カスケード(1024) + 25ステップ + 入力画像の投影。細部が必要なとき。約14分 |
| 高ポリゴン (最大) | 面数48万 + 4096テクスチャ。ディテールは +5% 程度、51MB |
| ゲーム向け最適化 | + ポリゴン削減 (既定2万面) + UV再展開・リベイク |
| リグ付き生成 | + ヒューマノイド骨格の自動生成とスキニング |

メッシュ修復 (`repair_mesh`) は**全プリセットで既定オン**。入力画像の投影
(`project_texture`) は `最高品質` のみ既定オンで、他は詳細設定から有効にできる。

所要時間はプリセットごとに実測平均を記録して表示する (未計測のうちは「未計測」と出る。
推測値は表示しない)。

「詳細設定」でシード、解像度 (512/1024/1024_cascade/1536_cascade)、目標面数、
テクスチャ解像度などを個別に上書きできる。エンジンに `mock` を選ぶと、
TRELLIS.2 を使わずシルエット押し出しのダミーメッシュで
パイプラインとビューワの挙動を確認できる。

サーバを立てずに CLI から回すこともできる:

```bash
.venv/bin/python scripts/run_pipeline.py images/usa.png --preset rigged
```

見た目を確認したいときは Blender でオフライン描画できる
(ブラウザのキャンバスは環境によって読み出せないため、自動検証にはこちらを使う):

```bash
.venv/bin/python scripts/render_glb.py data/jobs/<id>/result.glb -o out.png
```

| オプション | 用途 |
|---|---|
| `--flat` | テクスチャを外して形状だけ見る |
| `--cull` | 裏面を描かない (穴が背景色で見える) |
| `--unlit` | ライティング無しでアルベドをそのまま描画 |
| `--ortho` | 正射影 (投影の位置合わせ確認用) |
| `--yaw <rad>` | 水平回転 |

1回転する動画も書き出せる (Blender 1回起動で全フレーム描画 → ffmpeg で結合):

```bash
.venv/bin/python scripts/turntable.py <glb> -o out/turntable.mp4 --max-mb 95
```

### 設計上の要点

**エンジンは別プロセス・別venv。** TRELLIS.2 はパイプラインのロードだけで100秒前後
かかるので、生成のたびにプロセスを起こすのは現実的でない。JSON Lines で会話する
常駐ワーカーを立て、モデルを温めたまま使い回す。TRELLIS も依存も stdout に大量に
print するため、ワーカーは起動直後に fd 1 を複製してプロトコル専用にし、
fd 1 自体は stderr へ繋ぎ替えている。

**ステージの追加は1箇所。** `Stage` を実装して `pipeline/presets.py` の
`build_pipeline()` に差し込む。各ステージは `applies(params)` で自分が動くかを
判断し、`ctx.get(KIND_MESH)` で前段の出力を取って `ctx.put(...)` で上書きする。
LOD生成やフォーマット変換を足す場合も同じ形になる。

**ジョブは1本ずつ。** Metal デバイスを実質占有するのでワーカースレッドは1本。
キューの位置は API から返す。

## テクスチャ品質について

TRELLIS.2 のボクセル属性は
`base_color(0:3) / metallic(3) / roughness(4) / alpha(5)` の6チャンネル。
見た目の破綻はこのアルファの扱いに起因するものが大半だった。

### 1. 半透明になる問題

`o_voxel.postprocess.to_glb` はベイクしたアルファの最小値が 250 未満だと
マテリアルを **`alphaMode: BLEND`** で出力する。生成モデルのアルファは
広い範囲に分布するため常に BLEND になり、モデル全体が半透明になって
内部の面や裏側まで透けて重なる。結果として「灰色の斑模様」「金属質」に見える。

`ExportStage` が `alphaMode` を `OPAQUE` に倒して正規化する
(glTF 仕様上 OPAQUE ならアルファは無視されるので、テクスチャの
書き換えは不要。スキンやアニメーションにも触らない)。
`force_opaque: false` で無効化できる。

### 2. 暗い・色がずれる問題

生成物が全体に暗く、特に肌が黒く沈む。原因は2つで、**ガンマが支配的**。

**(a) ガンマ補正が抜けている (主因)。**
TRELLIS.2 の `base_color` はリニア空間の値だが、`o_voxel.postprocess.to_glb` は
`attrs * 255` をそのまま baseColorTexture に書く。glTF はこれを sRGB として
解釈するので、中間色だけが暗く沈む (白は 1^(1/2.2)=1 のまま変わらないため
「影が乗った」ように見える)。trellis-mac 同梱の KDTree ベイカー
(`backends/texture_baker.py`) は同じ補正を入れているので、Metal 経路の抜けと言える。

**(b) アルファの乗算 (副次)。** `base_color` はアルファが乗算された状態で出てくる。

Blender でライティングを通して描画し、参照画像と部位ごとに比べた結果:

| 処理 | 髪/頭 | 上半身 | スカート | 脚 | 平均誤差 |
|---|---|---|---|---|---|
| 参照画像 | 241,226,239 | 230,228,234 | 212,230,242 | 246,235,238 | — |
| 無補正 | 113,101,115 | 129,128,135 | 133,148,170 | 94,120,149 | 105.5 |
| ガンマのみ | 172,163,171 | 180,180,184 | 181,188,197 | 164,175,189 | 54.8 |
| 乗算解除のみ | 126,118,135 | 132,130,138 | 152,167,190 | 97,122,152 | 95.2 |
| **両方 (採用)** | 178,172,180 | 182,182,185 | 188,196,206 | 165,177,190 | **50.0** |

ガンマだけで誤差が48%減り、乗算解除でさらに9%減る。両方を既定にしている
(`base_color_gamma` 既定 2.2、1.0 でガンマ無効)。

**評価はアルベドではなく描画結果で行うこと。** アルベドのテクセル値を直接
参照画像と比べると、ガンマをいくら上げても誤差が単調に減り続けて最適値が
決まらない (レンダラのライティング分を無視しているため)。
`scripts/render_glb.py` が Blender でオフライン描画するので、これで比較する。

### 3. 色がシードで変わる

上記を直したうえでも、部位によっては色がサンプリングのばらつきに左右される。
同じ入力画像で髪の色を測った例 (参照は `[186,192,213]` の淡い青):

| seed | 髪 (頭部) |
|---|---|
| 42 | `[158,141,142]` 茶系 (外れ) |
| 7 | `[120,138,194]` 青系 |
| 2024 | `[162,166,195]` 淡青 (ほぼ一致) |

**色が明らかにおかしいときは、まずシードを変えて数回試すのが早い。**
バグではなく拡散モデルのばらつきなので、パラメータをいじるより効果がある。

### テクセル密度

TRELLIS.2 のベイカーはボクセルクラスタ単位で UV チャートを切るため、
2万面のメッシュでも約4,800チャートができる。1チャートあたりの
テクセル数が少ないとチャート境界が混ざってディテールが潰れる。

実測 (同じ入力画像、seed=42):

| 設定 | 面数 | テクセル/面 |
|---|---|---|
| 20万面 / 1024² (upstream 既定) | 182,813 | 5.2 |
| 20万面 / 2048² (`テクスチャ付き生成`) | 182,944 | 23.0 |
| 2万面 / 1024² (`ゲーム向け最適化`) | 19,044 | 55.1 |
| 1024パイプライン / 2048² | 5,235 | 801 (メッシュが粗すぎ、アトラスの大半が余白) |

UI の「モデル情報」に**テクセル/面**を出しており、30 を下回ると警告が付く。

### 4. 顔などの細部が潰れる問題

原因は3つあり、いずれも大きい。

**(a) 既定が低解像度で、しかもカスケードを使っていなかった (最大の要因)。**
`pipeline_type` の中身は次のとおりで、**モデル自身の既定は `1024_cascade`**。

| pipeline_type | 疎構造の解像度 | 形状ラテント |
|---|---|---|
| `512` | 32 | 512 |
| `1024` | **64** | 1024 |
| `1024_cascade` | 32 | 512 → 1024 に詰め直し |
| `1536_cascade` | 32 | 512 → 1536 に詰め直し |

`1024` は疎構造まで 64 に上げるためメッシュが細かく分断され、穴が増える。
カスケードは疎構造を 512 と同じ 32 に保ったまま形状ラテントだけ高解像度で
詰め直すので、**繋がりを保ったまま細部が出る**。実測 (同じ画像・seed=42):

| 設定 | 面数 | 穴 | 参照との色の誤差 | 所要 |
|---|---|---|---|---|
| `1024` | 168,415 | 10.8% | 50.2 | 12分 |
| **`1024_cascade` (採用)** | 153,650 | **6.6%** | 26.2 | 14分 |
| `1536_cascade` | 98,580 | 7.1% | **23.6** | 35分 |

`1536_cascade` は色の誤差だけ見ると最良だが、生の形状が2,409万面になり、
ベイク前に20万面へ落とす際の120倍圧縮でディテールが潰れる (顔がぼやける)。
面数も 98,580 まで削られるため採用していない。使うなら `target_faces` を
上げる必要があるが、今度はテクセル密度が足りなくなる。

`max_num_tokens` (既定 49152) を上げるとカスケードが保持する
トークンが増え、さらに細部が残る。

**(b) 余白の多い画像で被写体が縮んでいた。**
TRELLIS の前処理は「max辺を1024に縮小 → 背景除去 → 被写体で切り出し」の順なので、
2816x1536 の中央にキャラが立っているような画像だと、縮小の時点でキャラが小さくなり、
顔が45px程度しか残らない。ワーカーが**元解像度のまま先に被写体を切り出して**渡すように
した (`autocrop`、既定オン)。実測で 2816x1536 → 919x1536 に切り出される。

**(c) 入力画像は背景を透過させておくとよい。**
アルファがあれば背景除去 (RMBG) を経由せず、前処理がそのまま被写体を切り出す。
1024x1536 の透過画像で顔が約110px 確保できた。

### なぜ生の面数から大幅に削るのか

生成直後の面数はモデルの解像度に応じて桁が変わる (1024_cascade で約900万面、
1536_cascade で約2,400万面)。これをベイク前に落としている。

  生の形状 → `fast_simplification` で 60万面 → `to_glb` 内部の cumesh で 20万面

20万面という数字は上流 `generate.py` のハードコードで、コメントには
「mtlbvh が巨大メッシュでクラッシュするのを避けるため」とある。
つまり**品質基準ではなく安全マージン**。実際に上げても落ちなかったので
上限は緩めてある (`target_faces` は200万まで、`texture_size` は4096まで)。

**事前簡略化を緩めると逆に悪化する。** 「cumesh はトポロジー修復を持つのだから
多く渡したほうが良い」と考えて上限の 300万面を渡したところ、cumesh の cleanup が
かえって多く捨て、境界エッジ 6.4% → 8.1% / 面数 157,877 → 100,548 と悪くなった。
60万面が実測での最良値 (`PRE_SIMPLIFY_FLOOR`)。落ちたときだけ段階的に小さくする
フォールバックを入れてある。

`target_faces` を 50万に上げても効果は薄く、見える穴は 3.0% → 2.8% しか改善せず
ファイルが 36MB に増えるだけだった。

ただし**上げてもディテールはほとんど増えない**。理由は2つ。

**(a) テクスチャはボクセル属性の解像度が上限。**
表面ボクセルが約340万個に対し、2048² は 4,194,304 テクセルで
**既に約1テクセル/ボクセル**。4096² (16.7M) にしても4倍の過剰サンプリングに
なるだけで、補間しているだけで情報は増えない。

**(b) 面数を増やしてもテクセル密度とのトレードオフになる。**
1チャートあたり30テクセルを切るとチャート境界が滲むので、面数を上げるなら
テクスチャも上げる必要がある。

実測 (1024_cascade、同じ画像・seed=42。シャープさ = ラプラシアンの標準偏差):

| 設定 | テクセル/面 | シャープさ | 斑点率 | ファイル |
|---|---|---|---|---|
| 20万面 / 2048² (`最高品質`) | 21.0 | 7.89 | 0.06% | 13MB |
| 48万面 / 4096² (`高ポリゴン`) | 35.0 | 8.30 (+5%) | 0.06% | 51MB |

**ディテールの本当の上限はボクセル属性の解像度**であって、削減率ではない。
生の2,400万面という数字は等値面抽出のテッセレーションであって、
情報量そのものではない。

### テクスチャの追従度 (texture_guidance)

`pipeline.json` の既定では**テクスチャのサンプラだけ guidance_strength が 1.0**
(= 実質ガイダンス無し) になっている。形状側は 7.5。ここを上げると入力画像への
追従が強くなり、実測では単調に改善する (1024_cascade、同じ画像・seed=42。
シャープさ = ラプラシアンの標準偏差):

| texture_guidance | 色の誤差 | シャープさ | 彩度 |
|---|---|---|---|
| 1.0 (pipeline.json の既定) | 26.2 | 7.89 | 12.9 |
| 3.0 | 24.3 | 8.60 | 13.4 |
| 6.0 | 22.4 | 9.20 | 13.4 |
| **7.5 (採用)** | — | — | — |
| 10.0 | **20.5** | **10.42** | 13.2 |
| 参照画像 | — | — | 37.6 |

10.0 が最良だが、彩度が 6.0 をピークに反転し始めており CFG の過剰域が近い。
1枚の画像への過剰適合を避け、モデル自身が他のサンプラに使っている 7.5 を
既定にしている。もっと攻めたい場合は詳細設定の「テクスチャの追従度」で上げられる。

なお `max_num_tokens` は `1024_cascade` では効かない
(`hr_resolution == 1024` で即 break するため)。`1536_cascade` 専用で、
トークン数が上限を超えたときに解像度を128刻みで下げる安全弁として働く。

### 5. 面が欠けて見える問題

**主因はジオメトリではなく書き出しだった。** 3つが重なっていた。

1. **面の向きがばらばら。** 実測で外向き 50.3% / 内向き 49.7%、符号付き体積も
   ほぼ 0 でほぼランダム。
2. **`doubleSided` が立っていなかった。** エンジンの出力は `true` なのに
   `save_glb` が glTF の既定 (`false`) のまま出していた。
3. **法線を書き出していなかった。** 描画側がワインディングから法線を作るので、
   1 の乱れがそのまま陰影の破綻になる。

この3つが揃うと、裏面を描かない環境 (Unity / Unreal / 一般の glTF ビューワ /
Blender のソリッド表示) で内向きの面が丸ごと消える。実際 `最高品質` の出力は
胸元が抜けて中が見えていた。現在は `save_glb` が `doubleSided: true` と法線を
書き出し、修復ステージが向きを揃える。

亀裂そのものも残っている。**UVシームで頂点が分割されるため、位置で溶接してから
数えないと正しく測れない** (溶接前は境界エッジ 62%、溶接後は 6.4%)。

修復ステージ (`repair_mesh`、既定オン) は numpy で次の3つを行う。既存の頂点・面・UV
は変更せず、面と頂点を足すだけなので形状も UV も壊れない。

| 処理 | 内容 |
|---|---|
| `orient_faces` | 隣接面が共有辺を逆向きに辿るよう BFS で揃え、成分ごとの符号付き体積で外向きに直す |
| `fill_holes` | 境界エッジの**連結成分**ごとに最適平面へ投影して並べ替え、扇状に塞ぐ |
| `drop_specks` | 本体に対して極端に小さい孤立したかけらを落とす |

境界ループを辿る実装だと出発点に戻れた鎖しか塞げず、非多様体の分岐が多いため
全体の 6% しか埋まらなかった。連結成分ごとに扱うことで **6.4% → 4.4%** まで下がる。

塞ぐ三角形は頂点を複製し、UV は**その三角形が接するふちの1点**に揃える。UV を潰すのは
穴の周囲が別々の UV チャートにまたがることが多く、素直に継ぐとアトラス上で
無関係なチャートを塗り潰すため。穴ひとつにつき1点だけ使うと、そこが髪だった場合に
穴全体が髪色の平らなパッチになって顔の上で目立つ。

**`remesh` は使ってはいけない。** `o_voxel` の Dual Contouring はトポロジーを
作り直す際に、細い部分 (レース・フリル・髪束・脚) を丸ごと削除する。
再評価したところ元メッシュとのシルエット IoU が 0.37 まで崩壊した。
裏面カリングの有無で差分を取った「見える穴」も 3.0% → 7.3% と悪化している
(この指標は一枚板のフリルを常に穴と数えるので絶対値は過大だが、同じ条件での
比較には使える)。既定は `remesh: false`。
`remesh_project` も 1.0 にすると断片化した元表面に吸着してメッシュがばらばらになる。

Blender の穴埋め (`rigging/blender_fillholes.py`) も試したが、位置での頂点統合が
必要なうえ薄い三角形を潰し、塞いだ数より失う面のほうが多かった
(面 157,877 → 153,152)。現在は未使用。

### 6. 入力画像の投影 (project_texture)

ベイクしたアルベドの実効解像度は**ボクセル格子**で決まる。テクスチャを 2048 や 4096 に
しても元の信号がボクセル解像度なので情報は増えず、1024 解像度だと顔の目は20ボクセル
程度しかない。一方、入力画像そのものは顔だけで100px以上ある。

TRELLIS.2 は入力画像を正面とする正規化された姿勢でメッシュを作る (実測でメッシュと
入力の縦横比が 2.177 / 2.168 と一致) ので、入力画像を正射影で投影し直せば、見えている
面に元の解像度の絵を貼れる。`最高品質` プリセットで既定オン。

裏面や横を向いた面には貼れないので、法線の向きで重みを付けてベイク済みテクスチャと
混ぜ、オクルージョンは深度バッファで判定する。テクスチャに細い線状のゴミが残る失敗が
三通りあり、それぞれ対処が違う。

| 症状 | 原因 | 対処 |
|---|---|---|
| 目の輪郭に沿う青緑の枠 | UV チャート間の隙間はどの三角形にも属さず投影が原理的に届かない。ベイク時のパディングで入った色が残る | `gap_texels` でチャートの縁から数テクセルだけ埋める。深く埋めるとアトラス上でたまたま近い無関係なチャートから色を引く |
| ベイクが透けて縁が見える | 正面度はこちらを向いた面でも 0.4 程度にしかならない | `full_weight` を超えたら投影で完全に置き換える |
| 頬へ伸びる細い筋 | まぶたの溝の壁など、正面度が上がりきらない帯 | `solid_weight` 未満のテクセルを同じチャートの中で 3x3 の平均で `pad_texels` 回広げる |

`min_facing` はこれらの副作用を抑える栓で、下げすぎるとスカートの裏地のような
真横を向いた面まで投影されて色が破綻する。

シルエットを超えて位置を詰める `project_row_warp` (行ごとの幅合わせ) と
`project_dense_align` (ベイクで作ったモデルの正面画と入力画像のブロックマッチング) も
実装してあるが、**既定は無効**。顔の目の形は良くなる一方で、髪のように 2D と 3D で
対応の付けようがない場所で変位が暴れ、髪に顔のテクスチャが乗る場合があった。

### 効果が無かった検証

- **ビューワのミップマップ無効化** — チャート間のにじみを疑ったが変化なし
  (パディングの無いアトラスでは無効化自体は妥当なので残してある)。
- **`grid_sample=torch`** — upstream が flex_gemm 未導入前提で当てている
  パッチ経路。切り替えると同心円状のモアレが出て明確に悪化した。
  upstream の「flex_gemm の方がベイクがきれい」という記述を裏付ける形になった。
  設定として残してあるが、既定の `auto` (flex_gemm) を推奨する。

## オートリグについて

`rigging/skeleton.py` は学習ベースのオートリグ (UniRig 等) ではなく、
CUDA を要求しない範囲で実用にするための幾何ヒューリスティック。

- Y軸方向に128スライスして、各断面の幅と重心を取る
- 幅が細くなる位置から首と腰を決め、そこから胴のチェーンを引く
- 脚は腰から下を左右に分けて断面重心を追跡する (曲げた脚にもある程度追従する)
- 腕は肩から胴半径の外に出ている頂点群を取り、肩からの距離の分位点で肘と手首を置く
- 当たらなかった部位はボーンを出力しない (部分的な骨格として使える)
- 縦横比が低い形状 (車など) はヒューマノイドとして扱わず、リグを付けずに終わる

スキニングは Blender をヘッドレスで叩き、次の順で試して被覆率90%以上になった
方式を採用する:

1. 自動ウェイト (ヒートマップ) — 品質は最良だが水密メッシュを前提にしている
2. エンベロープ — ボーン長に比例した半径を設定して実行
3. 距離ベース (自前実装) — ボーン線分までの距離から上位4本を正規化。品質は劣るが必ず全頂点に乗る

**実際にはほぼ 3 が使われる。** 生成メッシュは非水密なので 1 は
`Bone Heat Weighting: failed to find solution` で失敗し、被覆率 0% になる。

距離ベースは Euclid 距離なので、体に沿って垂れた腕が近くの布を巻き込む
(実測で前腕が 28,222 頂点を受け持ち、スカートが手と一緒に動いた)。
影響半径をボーンごとに分けると軽減できる。手足の実測値は 0.03〜0.05
(身長 1.0 に対して) で、胴は衣装ごと受け持たせるため 0.12〜0.18 が目安。

採用された方式と被覆率はモデル情報パネルに出る。動作確認用に `Idle` という
簡易アニメーションも焼き込むので、ビューワで動かして破綻を見られる。

**限界:** 直立した全身ヒューマノイド向け。四足動物、機械、極端なデフォルメ、
腕が胴に密着したポーズには当たらない。指のリグは作らない。

## 設定

`.env.example` をコピーして `.env` を作る。主な項目:

| 環境変数 | 既定値 | 意味 |
|---|---|---|
| `I23D_PORT` | `8100` | 待ち受けポート |
| `I23D_ENGINE` | `trellis` | `trellis` / `mock` |
| `I23D_TRELLIS_DIR` | `vendor/trellis-mac` | trellis-mac の場所 |
| `I23D_DATA_DIR` | `data` | 画像とジョブ成果物の保存先 |
| `I23D_WORKER_IDLE_TIMEOUT` | `0` | アイドル時にワーカーを落とすまでの秒数 (0で常駐) |
| `I23D_BLENDER_PATH` | `/Applications/Blender.app/Contents/MacOS/Blender` | Blender の実行ファイル |

常駐ワーカーはメモリを約18GB 保持し続ける。使わない時間が長いなら
`I23D_WORKER_IDLE_TIMEOUT=900` などを設定すると解放される
(次回生成時にロードし直すので100秒前後の待ちが発生する)。

## 既知の問題

- **macOS の GPU ウォッチドッグ。** 長時間の Metal カーネルが打ち切られ、
  デコーダが空メッシュを返すことがある。外部ディスプレイを外す、
  `MTL_CAPTURE_ENABLED=1` を付ける、`SPARSE_CONV_BACKEND=none` にする、
  といった回避策がある。該当した場合はジョブのエラーメッセージに手順を出す。
- **Metal 拡張が無いと遅い。** `flex_gemm` が入っていないと sparse conv が
  純PyTorch実装になり、上流の計測では約10倍遅くなる。
- **単一視点の投影の限界。** 顔などは入力画像を正面から貼り直して精細にしているが、
  モデルの髪束と絵の髪束が数画素ずれると、絵の輪郭線が肌の上に落ちる。
  気になる場合は詳細設定で `project_texture` を切るとベイクのみになる。
- **メッシュに亀裂が残る。** 生成メッシュは境界エッジが 6% ほどあり、修復ステージで
  4% 台まで下げているが完全には塞げない。上流の `remesh=True` は
  トポロジーを作り直すためレースや髪束が消えるので使っていない。
